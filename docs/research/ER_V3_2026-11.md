# ER v3: supplier blocking and stratified active learning (2026-11-07, branch `er-v3`)

Queue item 29, which follows MATH v2 (f) (`docs/research/MATH_V2_2026-11.md`). **All data is SYNTHETIC.** The
generators in `crates/kizuna-bench/src/er_eval.rs` and the methods were written by the same team, so these numbers
show behaviour on known patterns, not accuracy on real supplier masters. Every number below comes from a run of the
command named with it, on commits 49d3085 (before) and f94b74d / f64045d (after), all with a clean worktree. The JSON
files record the commit, the seed and the environment.

**Humans decide.** Blocking only proposes pairs. A dictionary reading never makes a pair `safe`. The review-order
model only orders the queue and adds an advisory `suggested_p_match`. Every pair still needs a human decision in
`POST /entities/decisions`, and nothing is merged automatically.

## 1. Blocking: why supplier pairs never surfaced

Command: `cargo run --release -p kizuna-bench --bin kizuna-er-blocking -- --out reports/er/er_blocking_{before,after}.json`
(seed 20261105, default v2 config). The tool reports pair recall (true pairs that blocking produces / all true pairs)
and breaks down the missed pairs by the script of each name's core (legal form removed) and by variant.

**Cause (measured, 49d3085).** Every one of the 526 missed pairs (seed 20261105, 300 entities) has a **kanji** name on
one side and its **reading** on the other: 47 kanji–kana pairs plus 223 kanji–Latin pairs by raw-string script, and
the 256 "kanji–kanji" pairs turned out, on inspection, to be katakana names with a 株式会社/(株)/(有) legal form. By
variant: romaji 112, romaji_macron_upper 103, katakana_reading 101, kana_small_or_long_vowel 76, halfwidth_katakana 67,
and the rest are second-order (a kanji-variant or legal-form form paired with a reading form). v2 kept a romaji key
only for kana/Latin names (`CompanyKey.romaji` was `None` when a name had kanji, because there is no reading
dictionary). So a kanji form shared no sorted-neighbourhood key, prefix, q-gram or comparison field with
トウカイセイキ or Tokai Seiki Co., Ltd. Legal suffixes, full-width spaces and itaiji were already folded and were not
the cause. No pair was lost by scoring before the fix. Blocking lost them all.

**Fix (f94b74d).**
- `v2::reading`: a built-in list of 191 common company-name words: business types (精機, 工業, 製作所, …),
  regions/prefectures/cities, common prefix words (東洋, 昭和, 丸一, …) and common family names. The kanji core is
  segmented greedily (longest word first, katakana passes through). **Only when every character is covered** does
  each reading (≤ 4 alternatives, e.g. 日本 = ニッポン/ニホン) become a folded romaji key (`CompanyKey.reading`).
- Blocking: readings share the romaji key space (sort key, `r:` prefix, `r:` q-grams). They also get **exact
  reading blocks** (`r=<romaji>`, capped like the other exact blocks at 256 records). The exact blocks were needed
  for 450 entities, where both 神田工業 and 神田興業 read *kandakogyo* and the sorted-neighbourhood window (4) was too
  crowded.
- Comparison: the existing reading field γ₁ now also compares a **dictionary reading against a written reading**
  (kanji vs kana/Latin). Two kanji names are never compared by dictionary reading, because 工業 and 興業 read alike.
  The first attempt was a separate fourth field, and it failed: EM learned m ≈ 1.0 for it, and the threshold
  computation (which treats every field as present) then dropped 850 of 1514 true pairs on the 450-entity set.
  Merging the reading into γ₁ fixed that.
- `fold_romaji`: enlarged small kana now fold like the small forms (シヨーワ = ショウワ via `sy→s`, `ty→t`; ニツポン =
  ニッポン via geminate folding `kk/pp/tt/ss` and dropping an enlarged ツ between a vowel and k/p/t/s). This is
  approximate: a real マツカワ folds the same way as マッカワ. It is a candidate key only.

The unseen-places set (`er_eval::ja_suppliers_unseen`) uses 15 place names that are deliberately **not** in the
dictionary (甲府, 宇都宮, 松江, …). On it, the dictionary does nothing, as designed: those kanji names get no reading,
and recall stays where v2 was. The 1.000 on the main sets holds only because the dictionary covers every word the
generator uses (30 places, 15 business words). That is the main caveat of part 1.

Effect on the v2 listing for suppliers 300 (`kizuna-er-compare --runs 3`, listed pairs counted as predicted
matches): precision 0.843 → 0.940, recall 0.446 → 1.000, F1 **0.583 → 0.969**. Review load rises from 502 to 1010
listed pairs, 904 of them `requires_human_review`, mostly from the ambiguous-cluster rule (a key linked to two or more
others). Median resolve time is 32 ms → 108 ms (1 run each, host not idle).

## 2. Active learning: why uncertainty sampling lost to random, and the fix

Command: `cargo run --release -p kizuna-bench --bin kizuna-er-active -- --seed S --out reports/er/er_active_v3_seedS.json`
for S = 20261105 (the 8 sets from MATH v2), 20261205 and 20261305. The simulated reviewer answers from the truth, and
the model is refit after every decision. F1 is over all true pairs, and unsurfaced pairs count as FN for every
strategy. Strategies as in MATH v2 (f): `before` = the current queue order (FS weight descending, static EM outcome
for unreviewed pairs), `weight_model` = same order with model suggestions, `random`, and `after` = uncertainty
sampling (MATH v2). `stratified` is the new strategy.

**Diagnosis (measured, `ER_DIAGNOSE=1`).** The part comparison vectors take only **11–15 distinct patterns** across
2 000–12 000 queue items, and every item of a pattern has the same log-odds. On the three failing sets:
- *Uncertainty sampling never queries the patterns where the errors are.* On sparse 5000 / default, all 86 remaining
  errors at k = 0…2000 are false negatives in patterns that the factorized model calls confident non-matches:
  `[4,1,0,0]` (one character apart, digits differ: 60 FN of 203 items), `[6,1,0,0]` (14 FN of 14) and `[5,1,0,0]`
  (6 of 6). Uncertainty sampling spends all 2 000 reviews on 4–6 other patterns, and **100 % of its queried items are
  true matches**.
- *The labels it collects are biased and move the global model the wrong way.* Because it only queries matches, the
  match share p rises from 0.025 to 0.995 and the m counts concentrate on the queried levels. On dense 5000 / broad, p
  goes from 0.049 to 0.987 by k = 2000 with 301 FN unchanged. The conjugate model treats a non-random sample as
  representative, so the confident-but-wrong patterns never become uncertain.
- This is sampling bias plus redundant queries (thousands of items with an identical γ), not a cold-start problem: the
  model starts from the EM fit, and random review works because its labels are unbiased.

**Fix (`v2::active::PatternModel`, `next_item_stratified`, `order_queue_stratified`; f64045d).** The new model
estimates each comparison pattern's match rate directly, as θ_γ ~ Beta(s·q, s·(1−q)). Here q is the EM FS posterior
clamped to [0.05, 0.95] and s = 2, and θ_γ is updated only by decisions on that pattern. Within a pattern, items are
reviewed in seeded random order, so each estimate comes from a random sample of its own pattern. The queue first
takes 3 probes from every pattern (largest pattern first; this gives a stratified random warm start and diversity
across patterns), then the pattern with the highest min(θ̂, 1−θ̂), with more remaining items breaking ties. The
clamp was added after the first version (no clamp) failed on sparse 5000 / broad (2089 reviews). There, an EM
posterior of 1e-19 kept `[4,1,0,0]` (11 % matches) at "certain" after 3 non-match probes. That run is reported below
as `f0`.

Summary over all 27 configurations (25 that reach 0.99):
- **Stratified vs current order: fewer reviews on 25 of 25** (1.3–37×, e.g. 2274 → 61). The default rule
  ("never worse than the current order on all 8 sets") is met, so stratified is now the review order of
  `GET /entities/candidates` (v2). The API previously listed pending pairs in pair-index (sorted key) order, not even
  by weight. It now recomputes the order from the EM parameters plus all recorded `entity_decisions` on every request,
  and adds `suggested_p_match` per pair and `stats.review_order` / `stats.decisions_used`.
- **Stratified vs random: fewer reviews on 25 of 25** (1.2–13×). The 3–4× loss to random is gone.
- **Stratified vs plain uncertainty: better on 14, worse on 11.** The losses are mostly the 1000-key sets (15 → 22,
  16 → 30, 48 → 69, 26 → 93) and 2 of 3 supplier sets (402 → 516, 516 → 811). There, the 3-probe warm start across
  11–15 patterns costs ~35–45 reviews that uncertainty sampling does not spend. Uncertainty sampling's failures were
  10–30× (e.g. 10 348 vs 1181), while stratified's worst loss to it is 3.6× (26 → 93).

Sensitivity (seed 20261105, 8 part sets + suppliers, `reports/er/er_active_v3_sensitivity.json`): with prior strength
s ∈ {1, 2, 5}, probes ∈ {1, 3, 5} and clamp ∈ {0.02, 0.05, 0.1} (one setting changed at a time), reviews to 0.99 move by −14 % to +26 % on the 5000-key and dense 1000 sets (e.g. dense 5000 broad 1181–1188, sparse 5000 default 55–77), and suppliers 407–520 (clamp 0.1 or probes 5 give 407).
probes = 1 is better on the small sparse sets (12 vs 22, 15 vs 30); probes = 5 is worse there (34, 44). The defaults
(s 2, probes 3, clamp 0.05) were set before this sweep, apart from the clamp, which was added after the f0 failure. No
clamp (f0) fails on dense 5000 / broad (1688) and sparse 5000 / broad (2089).

## Gaps

- **Dictionary coverage is the whole of part 1.** Kanji outside the 191 words gives no reading (unseen-places set:
  recall 0.4515, unchanged). Not done: per-character on/kun readings, learning readings from human-confirmed aliases
  (`entity_aliases`), a tenant-editable reading list, and a partial-coverage key (e.g. known business word + unknown
  place).
- Readings are guesses. 工業/興業 and 日本 (ニッポン/ニホン) are real ambiguities that a human resolves. The enlarged
  ツ fold can join マツカワ and マッカワ. More supplier candidates are listed (502 → 1010 on 300 entities).
- The stratified model ignores structure inside a pattern. On mixed patterns (typo vs sibling part, `[4,1,0,0]` at
  11–30 % matches) it can only review them all; part context (strict typo rule) is not a model field.
- The API order is recomputed per request (O(pairs) after `resolve`, ≤ 5000 keys). No UI change: the web list shows
  pairs in the order the API returns, and `suggested_p_match` is not displayed yet.
- Synthetic data only. Simulated reviewers never err, and a wrong human answer would bias a pattern's estimate.
- Multi-seed robustness covers 3 seeds. Seed 20261305 sparse 5000 cannot reach 0.99 for any strategy, because 98–106
  true pairs are never surfaced (part-number blocking/scoring, not addressed here).
