# KIZUNA red-team, 2026-11-05

Authorised red-team of our own code on our own local instance only. Snapshot: `main` at `0758242` (detached
worktree). Fixes are on branch `redteam` (not pushed).

## Setup

- Own database `kizuna_redteam` (created with `scripts/lib/db.sh` `kz_ensure_db`, existing `kizuna`/`kizuna_app`
  roles, migrated with `kizuna-admin migrate`). `kizuna_test`, `kizuna_preview` and `kizuna_pilot` were not touched.

  The in-process suite creates its own tenants and users for every role, with and without MFA sessions, plus WebAuthn
  soft keys.
- Reproductions: `crates/kizuna-api/tests/redteam_2026_11_05.rs` (13 tests, real PostgreSQL, run with
  `--nocapture` to print one `RT|attack|expected|actual` line per attempt) and `scripts/redteam.sh host:port` (raw
  socket probes; refuses non-loopback targets).
- OWASP ZAP and nuclei are **not installed** on this host, so neither was run. The raw-socket probes in

### Details

**F1.** Before the fix: `GET /api/v1/evidence/part/%00` returned 500, and so did `POST /auth/login` with
`"tenant":"a\u0000b"`. PostgreSQL rejects NUL in `text` (SQLSTATE 22021) and `\u0000` in `jsonb` (22P05), and
`From<sqlx::Error>` mapped every database error to 500. This caused log noise and 500-based alerting on
unauthenticated input. Fix: `crates/kizuna-api/src/error.rs` maps 22021/22P05 to `400 invalid_text`. Test:
`rt_idor_malformed_ids_and_error_leakage`.

**F2.** Before the fix: after `UPDATE tenants SET status='suspended'`, `POST /auth/refresh` returned 200 with new
tokens. The access tokens were already refused because `Principal` joins `tenants`, but the refresh family stayed
alive and could be used again if the tenant were reactivated. Fix: the refresh query joins `tenants` and treats a
non-active tenant like a disabled user. Test: `rt_session_and_token_attacks`.

**F3.** Before the fix, from `scripts/redteam.sh`: incomplete header block still open after 40 s, a 1-byte-per-5 s
drip still open after 45 s, idle keep-alive still open after 70 s. A separate probe held 1500 connections with
`/healthz` still answering, bounded only by the 524288 fd limit. `axum::serve` sets no hyper timer, so
`header_read_timeout` never applied, and `TimeoutLayer` only starts after the headers are parsed. Caddy in the pilot
mitigates this partly, but the API port itself was unbounded. Fix: new `kizuna_api::serve` accept loop with hyper
http1, `TokioTimer` and `header_read_timeout` 15 s (this also bounds keep-alive idle), at most 1024 concurrent
connections (accept waits for a free slot), and graceful drain on shutdown. Configured with
`KIZUNA_HEADER_READ_TIMEOUT_SECS` and `KIZUNA_MAX_CONNECTIONS` (documented in `.env.example`). After the fix: closed
after 15 s / 20 s / 15 s. Tests: `rt_slow_headers_are_cut_off` (in-process, 2 s timeout) and `scripts/redteam.sh`.

**F4.** Before the fix, an XLSX whose `xl/_rels/workbook.xml.rels` contained an `oleObject` relationship to
`file://203.0.113.9/share/x.xls` with `TargetMode="External"` was stored with status `accepted`. Only
`xl/externalLinks/` was checked. Fix (`evidence-core`): every `*.rels` part (stored or deflate, at most 1 MiB
inflated, at most 200 parts, `miniz_oxide`) is read. Any `TargetMode` other than a literal `Internal` quarantines the
upload. This covers entity-encoded and UTF-16 spellings. An unreadable rels part also quarantines. Scanner id is now
`kizuna-static-scan@2`. Tests: `rt_upload_attacks` and the unit test
`external_relationship_targets_are_found_in_any_spelling`.

### Held (no finding)

- **Tenant isolation.** No cross-tenant read or write on any of 57 routes using tenant A's real ids. Writes in B
  that cite A's artifact, claim or decision ids, or that name A's claims as `faulty_claims`, were refused with 400.
- **RBAC.** 261 denied role×route attempts: 243 returned 403, 18 returned 400 (body shape), and none returned 2xx.
  Privileged permissions without an MFA session were refused. An analyst cannot change their own role. Bursts of
  denials trigger automatic session revocation (19 revocations during the matrix).
- **Sessions.** Every login issues fresh tokens (no fixation). Each of these was refused:
  - refresh token used as an access token, and the reverse;
  - forged, tenant-swapped or tampered tokens;
  - the old access token after rotation.

  Refresh replay revokes the whole token family. Under a concurrent double spend, at most one request succeeds.
  Tokens are dead after logout and after an admin revokes sessions.
- **TOTP.** A used code cannot be replayed. Wrong codes with the correct password lock the account after 5 tries,
  then the per-account limit applies (429), and the correct code is still refused while locked. Malformed codes get
  4xx.
- **WebAuthn and recovery codes.**
  - Refused with 401: assertion/challenge replay, an old assertion on a new challenge, a cross-user key, a challenge
    presented under another tenant's slug, password-only login for a key-protected user.
  - A recovery code cannot be used for another user or reused, and codes from the superseded set stop working. The
    recovery session is not MFA-verified.
- **Rate limits.** Rotating `X-Forwarded-For` does not help with `trusted_proxy_hops=0` (429 at the 21st login). With
  hops=1, spoofed left-hand entries are ignored. Using many accounts from one IP hits the same per-IP limit. The heavy
  endpoints (`/reports`, `/audit/verify`, checkpoint verify) are limited to 6 per user and 20 per tenant per minute.
- **Uploads.** The following were rejected (415) or quarantined:
  - PDF JavaScript/OpenAction;
  - XLSM macros;
  - externalLinks;
  - a 100 MB zip bomb;
  - a `../` zip entry;
  - an ELF disguised as PDF.

  The billion-laughs and XXE workbooks went through the sandboxed worker and were refused (400 in about 0.2 s) with no
  `/etc/passwd` leak. A traversal filename is stored as `passwd`, CRLF/quote filenames get 400, and
  `max_upload_bytes+1` gets 413.
- **AI path.** Injection PDFs plus six hostile provider answers were tested: governance fields, `review_status`, an
  oversized reply, two JSON objects, 1e308 confidence, duplicate ids. Every run fell back to rules with 0 AI claims.
  No email (PII), no `tools` and no altered system prompt were sent. All claims stayed `unreviewed`.
- **App-role SQL.** All of these were denied:
  - UPDATE/DELETE/TRUNCATE on `audit_events` and `security_events`;
  - DISABLE TRIGGER, DISABLE RLS, DROP POLICY;
  - `session_replication_role`;
  - CREATE TABLE/FUNCTION;
  - writes to `tenants`;
  - DELETE on `sessions`.

  `row_security=off` makes the query fail rather than bypass RLS. With no tenant set, 0 rows are visible. A
  cross-tenant INSERT is refused by the policy. A forged audit row appended by the app role is detected by
  `/audit/verify` (`intact=false`, `HashMismatch`).
- **HTTP.** All of the following were rejected by hyper/axum:
  - CL+TE smuggling;
  - duplicate Content-Length;
  - `xchunked`;
  - chunk overflow;
  - bare CR and NUL in headers;
  - obs-fold;
  - 1 MB and 500-header requests (431);
  - an HTTP/2 preface.

  Also:
  - No CORS headers were returned for foreign or `null` origins.
  - Auth is bearer-only (no cookies), so CSRF does not apply.
  - Security headers are present on errors.
  - Error bodies contain no SQL, paths or panics.
- **Expensive endpoints.** 8 concurrent calls each to reports, verification and detection answered in under 1 s, or
  were refused with 429.
