# バックアップと復元（運用者向け）

このページは KIZUNA のサーバーを運用する人向けです。コマンドの詳細は
[docs/deploy/DEPLOYMENT.md](../../deploy/DEPLOYMENT.md) の 7〜8 節と
[docs/deploy/OFFSITE_RESTORE.md](../../deploy/OFFSITE_RESTORE.md) を参照してください。

## バックアップの内容
`scripts/backup.sh` は、データベース（`pg_dump`）と文書ストアを 1 つのアーカイブにまとめ、SHA-256 のマニフェストを付けて
GnuPG（AES-256）で暗号化します。`kizuna-backup.timer` により毎日 2:30 に実行されます。
`scripts/offsite-backup.sh` は、暗号化済みファイルを rclone でサーバー外にもコピーし、コピーを確認してから古いファイルを
削除します（リモートは 60 日、ローカルは 14 日経過後）。失敗した場合はアラートが送信されます。

**バックアップに含まれないもの**：バックアップのパスフレーズと `KIZUNA_DATA_KEY`。どちらもオフライン（パスワード
マネージャーや封筒）で保管してください。パスフレーズがなければバックアップは復号できず、データキーがなければ認証アプリと
セキュリティキーの登録はすべて失われます。

## 復元訓練（毎月、およびアップグレードのたび）
`scripts/restore-drill.sh <バックアップ> --tamper-test --report <ディレクトリ>` は、バックアップを復号して使い捨ての
データベースへ復元し、全組織の監査ハッシュチェーンと全文書のハッシュを検証します。さらに、破損したファイルが検出される
ことも確認します。終了コード 0 かつ `"tamper_test": "detected"` なら合格です。JSON のレポートは保管してください。
サーバー外のコピーを使う場合は、先に `scripts/offsite-fetch.sh` で取得します。SHA-256 が一致しないファイルは拒否されます。

## 実際の復元
1. `kizuna` サービスを停止します。
2. バックアップを取得して復号します。
3. `pg_restore` でデータベースを復元し、文書ストアを展開します。
4. 両方に対して `kizuna-restore-verify` を実行します。
5. 保管しておいたシークレット（`kizuna.env`）を戻してから、サービスを起動します。
6. `/healthz` を確認し、`kizuna-admin verify-audit <組織>` を実行します。

## アップグレード
先にバックアップを取り、復元訓練を行ってください。マイグレーションは前方向のみのため、ロールバックは「以前のバイナリ」と
「アップグレード前のバックアップ」の組み合わせで行います。
